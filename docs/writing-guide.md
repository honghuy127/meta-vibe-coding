# Writing guide

Write so a person can make a decision and an agent can recover the relevant
facts without guessing. Use English for shared repository documentation. Product
examples and quoted user input can use the intended audience's language.

## Write naturally

Write as a thoughtful colleague explaining something to another person. Use
natural, direct language, including in text generated by an agent. Professional
writing can sound conversational while remaining precise.

Start with the purpose, result, or decision, then explain what the reader needs
to understand or do. Use concrete subjects, active verbs, and familiar words.
Connect related sentences into focused paragraphs. Vary sentence length naturally;
do not force every point into a heading, list, or sentence fragment.

Avoid canned introductions, repeated conclusions, rhetorical question-and-answer
pairs, and inflated phrases such as “delve into” or “leverage a robust solution.”
Explain the actual reason rather than adding emphasis with “crucial” or “important.”
Do not invent awkward compound labels where ordinary words would be clearer.
These are editing cues, not a mechanical word blacklist. Keep necessary technical
terms and define them when the reader needs them. Read the prose aloud in review:
if it sounds like a template or advertisement, simplify it.

Avoid promotional claims, filler, repeated summaries, and unsupported words such
as “safe,” “optimal,” “production-ready,” or “proven.” State what the evidence
actually establishes. Keep a research hypothesis distinct from an observed result.

| Instead of | Write |
| --- | --- |
| “Leverage a robust, scalable solution.” | “Use a static site because the current lessons need no accounts or saved progress.” |
| “The system is secure.” | “This review checked that the example brief contains no credentials. Runtime security has not been assessed.” |
| “We need to configure persistence.” | Owner View: “To keep progress when you change devices, the service needs to store it.” |
| “Tests pass, so users understand the risks.” | “Software checks passed. User comprehension has not been evaluated.” |

## Write for the reader

**Owner View:** explain consequences for use, data, money, control, and ongoing
work. Ask questions owners can reasonably answer. Include only technical details
that help them choose. Do not ask them to choose a database to express a need.

**Developer View:** give explicit fields, constraints, acceptance criteria,
assumptions, and unresolved questions. Use stable names and state the meaning of
unknown values. An empty field, `false`, and “not yet known” are different states.

**Contributor docs:** identify the outcome, authoritative path, owner when needed,
and exact checks. Link to an existing explanation rather than duplicating it.
The two product views can explain the same decision differently, but must agree
on its substance and uncertainty.

## Make claims traceable

- Label assumptions, proposals, confirmed facts, and measured results explicitly.
- Distinguish a planned capability from one implemented and checked.
- For verification, state the command or procedure, result, and material limits.
  If not run, say so; do not imply that a plan or fixture is execution evidence.
- Support external factual claims with primary sources near the claim. Date
  estimates and changing facts such as provider prices; retain uncertainty.
- Label fictional examples. Do not include private participant records or real
  credentials in docs, prompts, screenshots, or model-output examples.
- Use `must` for a requirement, `should` for a recommendation, and `may` for an
  option. Reserve checkboxes for actionable checks, not decoration.

## Keep Markdown easy to navigate

- Use one H1 title per standalone document and descend through H2/H3 without
  skipping levels. GitHub issue and pull request templates start at H2 because
  GitHub supplies their title.
- Use sentence case for new headings. Keep the original proposal's wording unless
  changing its content deliberately; formatting cleanup need not rewrite it.
- Use relative links within the repository and descriptive link text. Link to
  sections for long documents. Avoid absolute machine-specific paths.
- Use short lists for parallel items or steps, tables for comparisons, and prose
  for reasoning. Do not repeat the same content in each form.
- Put a blank line around headings, lists, tables, and fenced code blocks. Specify
  a code-block language where useful.
- Wrap prose near 80–100 characters when practical; do not break links, commands,
  or tables solely to meet a width target.
- Use `YYYY-MM-DD` dates. For timed evidence, include a time zone. Use lower-case
  hyphenated filenames for new docs; retain standard names such as README.md.
- Keep executable commands copyable. Mark pseudocode and examples as such; do not
  present a future command as an available project check.

The proposal contains illustrative configurations and future capabilities. Those
examples establish intent, not current runtime contracts or verified cost claims.

## Keep documentation small

Edit the document that already owns the subject. Add a file only when it serves a
distinct purpose or audience that is awkward to address there. A routine change
does not need a new plan, summary, report, or handoff document.

Keep one authoritative explanation and link to it. Remove repetition and obsolete
instructions when updating a document instead of appending another version. Use
Git history for earlier wording; retain decisions and evidence that still matter.

When a file becomes hard to navigate, first cut duplication and improve its
structure. Split it only along useful subject boundaries, with a clear entry link.
Do not create many small files merely to meet a line-count target, or copy full
transcripts and generated output into contributor guides. Store necessary detailed
evidence separately and link to it. Avoid new indexes that repeat an existing one.

## Before review

Check that a new contributor can find the authoritative information, distinguish
what exists from what is planned, and identify the next action. Remove stale
status, duplication, and unexplained jargon. Verify links and headings, and update
connected documents when a decision changes their meaning. Check whether the
change can be shorter or fit an existing document without losing useful context.
